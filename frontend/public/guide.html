Architecture and methodology

A local code repair workbench with a separate, read-only portfolio. The dashboard shows selected recorded executions, not a live agent session.

How a local run works

A React and TypeScript dashboard talks to a FastAPI application. SQLAlchemy stores tasks, runs, attempts, findings and events in SQLite with WAL enabled. A separate worker claims durable jobs, renews a lease, and marks abandoned work as interrupted when it restarts.

The worker records baseline tests and static checks, then asks planner, implementer, validator and reviewer roles to produce validated structured outputs. It permits one revision. Execution status, test outcome and review verdict remain separate throughout.

The execution boundary

Public GitHub imports are pinned to resolved commits and bounded by size. Source lives under src/; evaluation tests and dependency files are protected from agent edits. Python uses pytest and Ruff. TypeScript uses Vitest and the TypeScript compiler.

Dependency setup uses a disposable container without credentials. Checks run in fresh offline containers as a non-root user, with a read-only filesystem, dropped capabilities, CPU and memory limits, and timeouts. Host directories and the Docker socket are never mounted into execution containers. Containers are not a guarantee against kernel vulnerabilities; unfamiliar code belongs on a dedicated execution machine.

Original benchmark suite

Twelve versioned tasks, six Python and six TypeScript, exercise interval boundaries, zero values, Unicode identifiers, partial pages, version comparison, UTC dates, duplicate records and moving averages. Each includes existing coverage and a separate protected regression test. The suite is intentionally small and does not estimate general coding ability.

An observed fix requires a failing baseline, all patched tests passing, no lost existing passes, and a passing static check. Completed and rejected-patch benchmark runs with failing baselines form the denominator. Infrastructure errors, interruptions, cancellations and imported repositories are excluded and reported separately. Passing an imported repository's tests does not prove its issue is resolved.

What the recorded examples mean

The first model examples use real CodexLB Responses calls for planning, implementation, validation requests and review. Because Docker was unavailable on the development machine, baselines and candidate checks ran in GitHub Actions. Provider credentials stayed local. The activity record identifies this staged protocol and the execution workflow. A deliberately incomplete comment-only patch serves as a labeled negative control, not a failed model answer.

Comparisons require the same source version, execution limits, prompt, rubric and recording protocol. Staged execution duration is not end-to-end agent latency. Usage is provider-reported; cost is shown only when pricing is configured.

Evidence downloads

Each download uses difftrial.bundle.v1 and includes source provenance, diffs, measured reports, findings, role summaries, events and SHA-256 artifact checksums. Exports allowlist fields and redact recognized credentials and local paths. Checksums detect changes to artifact content; they are not an independent signature of authenticity.

Running the application locally

The source workspace requires Python 3.11+, Node 22.12+, and a Linux Docker engine. Install the Python package, run difftrial doctor and difftrial build-runners, then start difftrial serve, difftrial worker, and the Vite frontend. The local API binds to loopback and stores credentials only in the process environment.

CodexLB uses its Responses adapter and CODEX_LB_API_KEY. Compatible APIs support Responses and Chat Completions; Ollama supports installed local models. The other integrations remain unverified until tested against an available runtime and configured endpoint.
